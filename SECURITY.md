# Security boundaries and vulnerability reporting

This is an experimental security-scanning integration. Scan findings are untrusted evidence, not proof of exploitability; an empty report is not a security guarantee. No paid inference or live detection-quality tests have been run for this integration.

## Intended boundary

The authenticated loopback Harness UI authorizes billable source transmission to the selected configured Harness provider. The agent tool has no start/validate operation. Workspace ownership is taken from the executing session registration for tool requests; UI requests use only registered workspaces and existing owned scan IDs. The HTTP API requires native Harness request authentication, loopback address/Host, a custom header and same-origin authorization for paid actions. A supplied `Origin` must exactly match the loopback Host; when `Origin` is absent, browser-controlled `Sec-Fetch-Site: same-origin` is required instead. Missing, cross-site, same-site, opaque and conflicting origins cannot authorize a paid action. The client restricts Fetch to `mode: 'same-origin'`; explicit per-action consent remains mandatory.

Provider/model choices and the default, including optional reasoning effort, come from `sessionController.modelCatalog()`, the authoritative native Harness input-picker catalog. There is no adapter-list fallback. Before inference, configured-provider/native-catalog membership and resolved model identity are enforced and any explicit reasoning effort is validated. The bridge binds the exact provider/model and verifies the prepared adapter route. The activated Security dropdown was verified with configured options including GPT-6.1-Sol; it is not a reuse of the native input component.

Native Codex speaks Responses to a container-local loopback endpoint. Framed requests cross container stdin/stdout to the Host transport, where `harness-gateway.mjs` translates them to `llm.prepareCall` and the prepared adapter stream. Existing Harness adapters own provider access and authentication. The bridge does not read raw credentials, directly forward to a fixed DeepSeek endpoint or require a separate plugin API key. The scanner's local credential command emits a dummy gateway token, not a provider credential. Fresh container state has no ambient Codex login, Host home, external MCP configuration, proxy or tracing configuration.

Native engine tools execute only inside the container. The bridge translates local tool schemas/calls/results but never invokes Harness tools. Hosted external tools, remote background/storage and provider/model changes are rejected. A failed boundary check stops the operation; the bridge does not silently fall back to another provider/model. Native request/stream retries are disabled, but prepared adapters may retain their own retries. Sanitized failures, not raw adapter/provider error bodies, are exposed to the engine.

The Docker container has no external network, writable source, writable root image, added capabilities, privilege escalation, Docker socket or Host credential. It receives the approved workspace read-only, private writable report state and limited tmpfs scratch. Bubblewrap is a nested sandbox; the outer Docker boundary still applies even when the engine requests broader tool permissions. Custom seccomp allowances permit only the documented namespace/mount setup and do not grant outer kernel capabilities.

Repository code and model output can be malicious. Executing tests, parsers or dependency code inside the scanner can exploit bugs in native components or the kernel; Docker is not a substitute for a separate VM for strongly adversarial repositories. Do not scan untrusted code on a machine holding high-value secrets merely because its source mount is read-only. Keep Docker, its kernel and scanner dependencies patched.

## Protocol and operational limits

- Consent permits source and findings to leave the machine for the selected provider under its configured adapter routing; it does not authorize arbitrary publication or source mutation. Review provider configuration and data policies before consenting.
- Only POST `/responses` for the bound model is accepted from the engine. Explicit input history is required; `previous_response_id` is unsupported. Opaque replay requires intact consecutive cached assistant groups, and missing, modified or evicted groups fail closed.
- The bridge supports text and local function/custom tools with automatic tool choice only. Multimodal and hosted tools are unsupported. JSON Schema requests become instructions, not guaranteed strict provider-native schema mode. Catalog membership alone does not establish adapter/model compatibility.
- Transport limits are four concurrent requests, 100 requests per operation, 16 MiB request JSON, 64 MiB response and 180 seconds per model request. The bridge bounds JSON/replay state at 64 MiB and caches at most 256 response groups. Deadline/request/concurrency/size ceilings bound operations, not dollar cost or every adapter retry. Cancellation cannot undo charges for a request already accepted by the provider.
- Docker creation has a 30-second managed-client timeout, but daemon-side creation can outlive the client. Durable, label-verified leases are reconciled at startup and every 30 seconds; cleanup removes immutable container IDs only after verifying the lease label. Uncertain absent `creating` leases remain tombstones indefinitely, and legacy unlabeled containers are not automatically removed. Cleanup/grace can exceed the scan deadline; interrupted runs are not automatically resumed.
- Export is report-only and requires no model inference, but JSON/CSV/SARIF may disclose source, paths and vulnerabilities. Do not commit local engine state or generated findings to a public repository without reviewing them.
- Engine source is mounted directly read-only; unsupported symlinks/submodules/worktree metadata outside the registered path are not automatically granted extra mounts.
- Engine state is kept in private directories outside Git worktrees. Durable Harness records/history also contain potentially sensitive findings. Automatic retention/deletion is not implemented; remove artifacts only after tasks and containers are stopped, using reviewed absolute paths.
- The full Host process, configured adapters and its filesystem/tool access are trusted. Same-origin UI authorization is not an unforgeable human-presence guarantee against an attacker or an unrestricted agent that already controls the Host/browser. Do not expose the local Harness endpoint or permit untrusted extensions to operate it.
- The engine model catalog is an original minimal authored template, not the removed third-party copied prompt catalog. Its planning hint is not a guarantee of provider reasoning behavior; Harness owns the selected provider reasoning configuration. No licensing claim is made for the removed copied prompts.
- The rebuilt image, activated runtime/picker and 101 offline tests (including real native scanner/local-tool/opaque-replay roundtrip through a synthetic Harness adapter) were verified. This does not establish real-provider compatibility, live detection quality or parity against known-vulnerability and negative-control repositories.

## Report vulnerabilities

Public repository: [TheSethRose/dsh-security](https://github.com/TheSethRose/dsh-security). Use GitHub's private vulnerability reporting when enabled, or contact the repository owner privately before disclosing exploit details. Do not post API keys, raw sensitive reports, private repository contents or working exploit credentials in public issues. Include the plugin revision, locally built engine image ID, Harness/Docker/kernel versions, the configured provider/model (without credentials), the boundary affected and a minimal non-sensitive reproduction.

If isolation or provider routing fails, stop the scan/plugin. Do not enable privileged mode, writable source, unconfined seccomp, provider/model fallback or silent kernel-policy relaxation as a workaround.
